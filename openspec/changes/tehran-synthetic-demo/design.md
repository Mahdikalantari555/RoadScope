# Design: central Tehran synthetic demonstration

## Approach

1. Define and version a small central-Tehran boundary polygon, buffer for boundary-crossing roads, network snapshot date and checksums. Choose the exact boundary before importing. Extract an Iran OSM PBF from Geofabrik, clip locally, retain source OSM IDs, `highway`, name/name:fa, oneway, bridge, tunnel and layer. Record extraction rules and license metadata. Do not commit PBFs, generated databases or tile bundles.
2. Convert the extracted streets to the existing segment/node/lixel model. Split where topology actually connects; do not connect geometric crossings when OSM topology/grade says otherwise. Preserve parent IDs and version mappings; validate connectivity and ambiguous grades, report excluded/missing attributes, and use a conservative analysis network when information is unknown. Clip/display consistently and distinguish the buffered analytic graph from the presentation boundary.
3. Make CRS and bounds dataset-aware or isolate profiles by process and database: Tehran metric EPSG:32639, exchange GeoJSON EPSG:4326, always longitude/latitude; Frankfurt remains EPSG:25832. Audit fixed `25832` column names, helpers, conversion calls, front-end UTM32 readouts, fixed coordinate presets, simulator assumptions and CRS/bounds checks. No process-global EPSG flip over existing data; if coexistence is not safely supported use separate databases/instances with explicit selection and documented limitation. Migrate only with backups and tests.
4. Generate seeded synthetic events on actual lixels in the Tehran network; store synthetic flags and generator seed, version and parameters independently from the fact that network geometry is OSM. The demonstration dataset remains exclusively synthetic in its incident content; no dummy or estimated exposure/weather may be presented as measured. Never use real-looking names or locations to imply actual historical incidents. Report counts, severity and time are illustrative. Keep simulation reproducible and avoid overwriting the Frankfurt database.
5. Drive map bounds, center, reset, spatial context, search, metric readout and allowed extent from dataset metadata, not fixed Frankfurt constants. Do not overlay Frankfurt-generated parks/river/grid. Use a configurable online tile provider with visible OSM attribution and policy compliance; allow disable/failure fallback. Check access from target environment; do not assume public OSM tile service is an SLA or allow bulk downloading.
6. Provide presentation mode that de-clutters without hiding attribution, synthetic labels, study area, incident-date/seed provenance or research caveats. Provide a documented fixed viewport, seed and state, and screenshot capture via browser; avoid claiming reliable export of cross-origin canvas absent verified CORS. Capture includes visible disclaimers; if a screenshot is produced, do not put binaries in Git by default.

## Safety and compatibility

The demo guard currently rejects any non-synthetic dataset. Mark demo incidents as synthetic while explicitly recording real network origin; never relax this guard to allow real reports in demo mode. Prevent demo operations and generated data from writing to real or legacy datasets. Preserve existing API behavior and protect legacy data; test profile switching/isolation. Real datasets and concurrent cross-CRS support are outside this change. Default or synthetic AADT, weather and model results are labeled and not interpreted as real Tehran measurements; disable an output where this cannot be guaranteed.

## Verification and rollback

Use a tiny, redistributable OSM-like test fixture with at-grade intersections, grade separation and disconnected segments; validate node topology, coordinate round-trip and metric distances, deterministic results, incidents-on-network, and import idempotence. Test Persian/English, zoom/reset and provenance, provider failure, existing Frankfurt startup and APIs, and performance on a documented viewport. Back up the database before migration, restore on failure, switch back to Frankfurt profile without deleting or mutating its data, and document external dataset removal and rollback.
